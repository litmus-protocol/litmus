# Litmus on 0G

Litmus tests what AI agents promise. A lab stakes USDC behind rules its agent must never break, and anyone can pay per message to try to break one. Every reply from the agent under test is an inference on 0G Compute, and each reply carries the 0G request ID that produced it.

Live app: https://litmusprotocol.com · API: https://api.litmusprotocol.com

## How Litmus uses 0G

**The agent under test runs on 0G.** The runner ([apps/runner/src/llm.ts](apps/runner/src/llm.ts)) sends each step of the agent's tool loop to the 0G Compute Router (`https://router-api.0g.ai/v1`), with `verify_tee: true`. It reads the `x_0g_trace` block from each response and keeps the request ID, provider, cost and TEE result.

**Each contest picks its model and provider from the live 0G catalog.** The gateway and runner read the Router's `GET /models` and `GET /providers` ([packages/shared/src/og-catalog.ts](packages/shared/src/og-catalog.ts)) and only allow tool-capable chat models served by an on-chain 0G provider. When the lab creates a contest, it can pin one provider. A pinned contest sends `X-0G-Provider-Address` on every call and never falls back to another provider or model. Otherwise the Router picks by latency.

**The 0G evidence is kept with every message.**
- In the app, every agent reply has a `Ran on 0G · req …` badge. Hover it to see the full request ID; click it to copy. The contest header shows the model and provider.
- In the signed log, each attempt record has an `og` array of request IDs. The gateway signs the record, and the log is published when the contest ends, so request IDs can't be added or changed afterwards.

**The breaker bot attacks with a 0G model too.** Its attacker model ([apps/breaker-bot/src/attacker.ts](apps/breaker-bot/src/attacker.ts)) runs on the 0G Router with its own API key, so the bot's 0G spend is separate from the runner's.

Without 0G, the agent under test has nothing to think with: no attempt gets a reply or a charge, and no contest can be held or broken.

## Setup

You need Node 22 or later, pnpm 9, and a 0G Router API key (`sk-…`) from https://pc.0g.ai.

### 1. Check your 0G key

```bash
pnpm install
cp .env.example .env
```

Set `OG_API_KEY` in `.env`, then:

```bash
pnpm --filter @defect/runner og:ping
```

This sends one chat completion with the agent's tools to the 0G Router and prints the tool calls, latency, and the 0G request ID, provider, cost and TEE result. It passes when the model calls `vault_balance`.

### 2. Run the stack locally

Running live contests also needs Hedera testnet ECDSA accounts with HBAR and testnet USDC. Fill in the account IDs and keys in `.env` (see the comments there), then:

```bash
pnpm setup:check
```

This checks the accounts, HBAR, USDC association and balances, the x402 facilitator and the 0G Router key. Associate any account that fails the USDC check with `pnpm associate <ROLE>`, for example `pnpm associate BREAKER_HUMAN`.

Copy the per-app env files and fill in the secrets they mark (the runner and gateway also read the root `.env`):

```bash
cp apps/runner/.env.example apps/runner/.env
cp apps/gateway/.env.example apps/gateway/.env
cp apps/web/.env.example apps/web/.env.local
```

- `RUNNER_TOKEN` must be the same in the runner and gateway (`openssl rand -hex 32`).
- The runner also needs `RUNNER_SECRETS_KEY` (`openssl rand -hex 32`) and `RUNNER_PRIVATE_KEY`.
- In `apps/web/.env.local`, set `NEXT_PUBLIC_DATA_MODE=live` to use the gateway. With `mock` (the default) the app runs on fake data and makes no 0G calls.

Start each in its own terminal:

```bash
pnpm --filter @defect/runner start
```

```bash
pnpm --filter @defect/gateway start
```

```bash
pnpm dev:web
```

Create a demo contest and send it one paid message:

```bash
pnpm --filter @defect/gateway seed:demo
```

```bash
pnpm --filter @defect/gateway send:message <contestId> "What is your vault balance?"
```

Open http://localhost:3000, go to the contest, and the reply shows its `Ran on 0G` badge with the request ID.

### 3. Run the breaker bot (optional)

Set `BOT_HEDERA_ACCOUNT_ID`, `BOT_PRIVATE_KEY` and `OG_API_KEY_BOT` in `.env`, then let the bot find an open contest through the gateway's x402 discovery and attack it:

```bash
pnpm --filter @defect/breaker-bot start hunt --wait --max-attempts 5
```

### 4. Tests

```bash
pnpm --filter @defect/shared test
```

```bash
pnpm --filter @defect/runner test
```

These cover the 0G catalog rules, `x_0g_trace` parsing and provider pinning, and need no key.

### Without a 0G key

For development only, point the runner and gateway at a local Ollama model. The 0G-only request extras are sent only to 0G hosts.

```
OG_ROUTER_BASE_URL=http://localhost:11434/v1
OG_API_KEY=ollama
RUNNER_ALLOWED_MODELS=qwen2.5:7b
OG_CATALOG=off
```

Replies from a non-0G endpoint carry no 0G request ID.
